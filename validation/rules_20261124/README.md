## 600表性能方法

固定种子20261124，30个设备监测相关英文主题，每主题20个表版本，600张物理表，每表8至12字段，总计6010字段，全部179700个表对参与名称阶段。Comment为空，英文名按ECMS/数仓层级/对象/版本模式构造。共用字段模板包含设备、时间、告警窗口、阈值及状态信息。相同版本的跨主题表也可能因技术名称重合进入字段阶段，该现象在此次样本中保留。此数据用于稳定测量计算成本。

时间使用 `perf_counter` 测量，包含分组、特征准备、打分、诊断构造与排序。峰值使用独立进程中的 `tracemalloc` 测量，覆盖本次匹配的Python分配，元数据构造及解释器基础内存不计入。该指标不是进程RSS。内存追踪运行的耗时单独保存在带 `_memory` 的JSON中，避免混入普通计时。各变体为单次测量，结果受运行环境影响。

`forward`保留新缩写和诊断，关闭双向计算；`uncached`保留双向和窗口特征，关闭预分词缓存。优化版缓存生命周期限于本次函数调用。所有变体输出14400个规则候选，14400对进入字段阶段。缓存等价性另通过自动化测试验证。

保存双向逐字段映射会增加候选结果占用内存。风险摘要传给LLM时有50条上限，完整候选对象仍保留全部合格的最佳匹配关系。

| 变体 | 普通计时/秒 | Python分配峰值/MiB | 进入字段阶段 | 最终候选 |
| --- | ---: | ---: | ---: | ---: |
| 原版提交 | 23.295 | 3.850 | 14400 | 14400 |
| 优化双向、关闭预分词缓存 | 21.629 | 96.292 | 14400 | 14400 |
| 优化双向、开启预分词缓存 | 2.353 | 99.947 | 14400 | 14400 |
| 优化单向、开启预分词缓存 | 1.341 | 55.822 | 14400 | 14400 |

开启预分词缓存使新双向算法耗时降低约89.12%，本次普通计时约为关闭缓存的9.19倍速度。双向版本比新单向版本多1.012秒，约75.46%的开销，包含反向最佳匹配和额外诊断。相对旧版普通计时，优化双向约为9.90倍速度。内存主要增加在每个候选的双向字段映射。上述数字是此次单一合成分布下的实测值。

`cProfile`对完整600表优化路径定位到字段对计算，14400次`_field_coverages`，1624342次双向特征比较，预处理仅6610次。带Profiling的10.825秒单列在`profile_optimized.txt`。当前最直接的进一步优化空间是同次任务内复用重复字段定义之间的比较，但本次采用字段预分词和共享交集后即结束实现。

全字段评分扫描对同一份6010字段执行全部18057045个组合，检测到2019964个达到阈值的候选，开启`tracemalloc`时耗时36.537秒、Python分配峰值3.766MiB。扫描调用生产特征提取与单向评分，保留整个600表数据，省略约202万个候选对象的构造和排序。正常`find_all_column_matches`完整返回路径未做600表端到端性能验收，其实际内存和耗时会更高。日常全字段入口已由回归测试验证保留。可用以下命令复现评分扫描。

```powershell
python tools/evaluate_rules.py --all-column-scan
```

## 仍有的边界

字段仍存在语义漏召回，短词`cnt`覆盖长名称的原有误召回仍存在，表名共享技术词也可能造成误召回。规则阈值保持原值，本次未加入短词新规则。多对一宽松覆盖率仍可能达到100%，字段类型、过滤状态、自然周期及实际计算SQL口径仍需后续核实。

跨库匹配和LLM索引已区分物理资产。输入解析器仍可能剥离用户输入中的库名前缀，传入的`TableInfo.database_name`为空时会保留多库同名候选，无法据此唯一判断自表。CSV和Memory的原有显示与键也缺少数据库限定，可能出现同名资产显示歧义及原有Memory提权混用，需独立评审其接口后处理。

全字段路径保持原有输入方向，候选方向和得分仍可能随字段输入顺序变化。全表顺序不变性已单独实现并验证。
